A physician inquiry, ready for your recruiting team in HubSpot.

Once a physician's inquiry is in HubSpot, an n8n workflow reads it, keeps to what the physician actually wrote, and leaves a review task with a proposed reply. Someone on your team decides what to send. The inquiries below are invented, with the fields of the Join Expedient form.

Six recorded runs where HubSpot or n8n misbehaves on purpose, then how the workflow starts, what it sends to the model, what it writes, and the files.

    For whoever looks after HubSpot and n8n

    The workflow is a reference, not something to switch on as is. It was tested on n8n in Docker against a HubSpot API simulator; no HubSpot account was used. Your properties, permissions, trigger and existing workflows have to be mapped before activation. It was built without access to your portal, so the first step is a run on your HubSpot sandbox.

    One way in

    The public Join Expedient form is a WordPress form (Gravity Forms), and the site loads HubSpot's tracking script. The workflow assumes that each submission reaches HubSpot as a form conversion on the contact, with Credentials and Message mapped to contact properties, through the Gravity Forms add-on for HubSpot or HubSpot's collected forms. That has to be checked first; if submissions do not arrive that way, the entry point changes.

    Every two minutes, a poller asks HubSpot's contact search for contacts whose recent_conversion_date is newer than its checkpoint, minus a ten-minute overlap. A returning physician who submits again counts as a new inquiry, because the submission time changes. The workflow's own writes never touch that property, so it cannot trigger itself.

    It needs a private app token, not HubSpot's "Send a webhook" workflow action, and it registers no HubSpot Trigger node, so it does not compete with a trigger you may already run in n8n.

    What the model sees

    Two fields, from an allowlist in the Configuration node, credentials and message, plus one yes or no flag: whether your team already has a record for this physician. Name, email, phone, owner, notes, history and attachments stay in HubSpot. One provider was tested, OpenAI's , with no fallback to another. A message too short to read never reaches the model.

    The model proposes; plain code checks. A suggested value whose quote cannot be found word for word in what the physician wrote is dropped and flagged. Routing to review is a rule, not a model judgment.

    What it writes, and what it never writes

    Suggestions go to their own group of contact properties (ai_inquiry_*), plus one task per open inquiry, assigned and due the next business day at 10:00 Pacific. It never writes lifecycle stage, owner or a staff-verified value; when a message contradicts the verified record, the task says so and goes to high priority. Nothing is emailed.

    When something fails

    A recovery ledger, in a Postgres database (the one n8n uses, if it runs on Postgres), records per submission, which effects already happened. A retry finishes the missing step instead of replaying everything: the model is not asked twice, the contact is not rewritten, and a task that may already exist is looked up by its reference before anything is created. After MAX_ATTEMPTS attempts (5 by default, 3 in these test runs) it stops and sends an alert that carries the submission reference and the failing step, never the message.

    Before it runs on your portal

    • First, check that join form submissions reach HubSpot as form conversions with Credentials and Message mapped. If they do not, the entry point changes.
    • Map your property names in the Configuration node; the README lists the eight to create.
    • Check which forms set recent_conversion_date on physician contacts, and set JOIN_FORM_NAME so only the join form counts.
    • Choose the owner who receives the tasks and the channel for alerts.
    • Run it against a sandbox or test portal first.

    Known limits

    • HubSpot keeps one value of the message property. Two submissions from the same physician inside one polling cycle leave only the latest text to read.
    • Not tested here: a real HubSpot portal, another model provider, a restore into a clean instance, a production VPS.
    • Model readings vary slightly from run to run; the checks above held on this run.
