    For whoever looks after HubSpot and n8n

    The workflow is a reference, not something to switch on as is. It was tested on n8n in Docker against a HubSpot API simulator; no HubSpot account was used. It was built without access to your portal, so the first step is a run on an approved test portal. Your properties, permissions, trigger and existing workflows have to be mapped before activation.

    One way in

    The public Join Expedient form is a WordPress form (Gravity Forms), and the site loads HubSpot's tracking script. The workflow assumes that each submission reaches HubSpot as a form conversion on the contact, with Credentials and Message mapped to contact properties, through the Gravity Forms add-on for HubSpot or HubSpot's collected forms. That has to be checked first; if submissions do not arrive that way, the entry point changes.

    Every two minutes, a poller scans a bounded window of recent_conversion_date values page by page, keeps only conversions from the form named in JOIN_FORM_NAME (mandatory: without it the poller stops and alerts), and records each submission once with its form fields frozen. The scan checkpoint moves only after the whole window has been read and recorded. The workflow's own writes never touch that property, so it cannot trigger itself. It needs a private app token, not HubSpot's "Send a webhook" workflow action, and registers no HubSpot Trigger node.

    What the model sees, and what n8n handles

    The workflow processes contact details in n8n and stores the reading and the draft reply in its recovery database. The model receives Credentials, Message, a known-to-team flag and what the physician's own earlier inquiries already said, not separate name, email, phone or history fields. Free-text messages are not automatically de-identified: whatever a physician types in Message goes to the model.

    One provider was tested, OpenAI's , with no fallback. Before production: an approved, company-owned model account and infrastructure, agreed rules on what input is permitted, retention and access rules, and a route for unexpected sensitive submissions.

    The model proposes; plain code checks. A value is kept only if its quote is in the message and the quote supports it: a state must be named in it, a call window must contain a time, a certification status must be about QME work. Anything else is dropped and flagged. A reply without content fails the attempt.

    What it writes, and what it never writes

    Suggested values go to their own group of contact properties (ai_inquiry_*); the quotes that support them go into the review task. There is one open review task per physician, with subsequent inquiries appended, assigned and due the next weekday at 10:00 Los Angeles time. It never writes lifecycle stage, owner or a staff-verified value, and never lowers a task's priority; a message that contradicts the verified record raises it to High. Nothing is emailed.

    When something fails

    A recovery ledger, in a Postgres database (the one n8n uses, if it runs on Postgres), records per submission its frozen fields and which effects already happened. Retries reuse a saved interpretation and skip steps recorded as complete; a task that may already exist is looked up by its reference before anything is created. Each attempt holds a lease with an owner token, checked before every write, so an attempt that outlived its lease stops without writing. Recorded work is retried even when the contact search is down. After MAX_ATTEMPTS attempts (5 by default, 3 in these test runs) it stops and alerts; an alert counts as sent only once the endpoint acknowledged it, and is retried otherwise. Alerts carry the submission reference and the failing step, never the message.

    Before it runs on your portal

    • First, check that join form submissions reach HubSpot as form conversions with Credentials and Message mapped. If they do not, the entry point changes.
    • Set JOIN_FORM_NAME to what your portal records for the join form.
    • Map your property names in the Configuration node; the README lists the eight to create.
    • Choose the owner who receives the tasks and the channel for alerts.
    • Run it on an approved test portal first.

    Known limits

    • HubSpot keeps one value of the message property. Two submissions from the same physician inside one polling cycle leave only the latest text to freeze.
    • Leases are fenced per submission; two different submissions from one physician claimed by two simultaneous polls could still race on the same task.
    • Not tested here: a real HubSpot portal, another model provider, a restore into a clean instance, a production VPS.
    • Model readings vary from run to run; the assertions below held on this run.
